最近在比较两个能给 AI Agent 用的浏览器工具：ego-browser 和 bsk。两者都能驱动本机已经登录的 Chrome，省去重新登录和搬 Cookie 的麻烦。我用同一个任务各跑了一遍，记录一下差别。

## 测试任务

打开部署站，用已登录的账号进到知识库维护页，点「新增」，读出「知识编码」输入框的 disabled 和 placeholder。任务不大，但涉及导航、点击和读 DOM 状态，正好能看出两个工具在多步操作和取值上的差别。

## ego-browser：一轮一个脚本

ego-browser 的用法是把一段 Node 脚本交给它执行：

```js
const task = await taskSpace("kb code check");
const page = task.page("p1");
await page.goto("http://10.0.15.33:32618/kb/KnowledgeList");
await page.waitForSelector("text=知识维护");
console.log(await page.snapshot());
```

每一轮是一个新进程，浏览器状态（task space、标签页、页面 label）保留，脚本里的变量不保留。所以多步流程要写在同一段脚本里：

```js
await page.click("@37", { label: "点击新增知识" });
await page.waitForSelector("css=.el-dialog");
const info = await page.evaluate(() => {
  const item = [...document.querySelectorAll('.el-form-item')]
    .find((el) => el.textContent.includes('知识编码'));
  const input = item.querySelector('input');
  return { disabled: input.disabled, placeholder: input.placeholder };
});
```

整个任务用了四轮：打开登录页、登录并跳转、点击加取值加截图、结束。快照里的节点自带 ref 和现成选择器；报错也具体，我用 `css:input` 时它直接列出两个候选（用户名和密码框），不用自己猜。它还复用了浏览器的登录态，用户名和密码是浏览器自己填好的。

限制也明显：它不是 Playwright，`locator()`、`expect()` 那套用不了，得按它自己的 API 写；每轮启动一个 Node 进程，大约一两秒。

## bsk：一条命令一个动作

bsk 是常驻 daemon 加命令行子命令，浏览器状态放在 daemon 里：

```bash
bsk session start --name "对比测试" --no-focus
bsk navigate "http://10.0.15.33:32618/kb/KnowledgeList" --session juby
bsk snapshot --session juby --max-tokens 1500
bsk click @e137 --session juby
bsk evaluate --session juby "[...document.querySelectorAll('.el-dialog .el-form-item')]..."
bsk session stop juby
```

好处是随手：想看什么就敲一条命令。`snapshot` 带 `@eN` 引用和上下文提示，大页面可以用 `--max-tokens` 截断。它还带 console 与 network 缓冲、下载捕获、元素截图、移动端模拟这些子命令，排查线上问题时很方便。

不顺的地方：多步流程要来回调用好几次；每条命令都会打印一行「有新版本 0.3.2→0.3.3」，看多了有点吵；中文参数走 Windows 命令行有编码风险，这次我全用 ASCII 选择器绕开。

## 差别的核心：状态放在哪

ego-browser 把浏览器状态放在 task space，把流程逻辑放在一次性脚本里；bsk 把浏览器状态放在 daemon，把操作拆成一条条命令。

这个差别决定了使用方式：写可重复执行的检查，用 ego 更顺，一次调用能跑完整个流程并输出一个 JSON；临时探查一个页面、抓网络请求或下载文件，用 bsk 更直接。

两边跑出来的结果一致：输入框 `disabled=true`，placeholder 是「保存后自动生成」。
