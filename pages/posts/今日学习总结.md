### Spring Boot 和 Spring 的区别

Spring 是偏底层的应用框架，主要负责对象管理、依赖注入和业务解耦。

Spring Boot 建立在 Spring 之上，用自动装配和默认配置把项目快速搭起来，并处理启动、部署和日常维护中的常见配置。

### HTTP 的 POST 和 GET 请求有什么区别

GET 通常用于读取资源，参数一般放在 URL 里；POST 通常用于提交数据，内容一般放在请求体里。

URL 能承载多少数据没有统一答案，不同浏览器和服务器都会有长度限制。参数过长时，GET 更容易碰到这些限制。POST 可以传多种类型的数据，包括文件。

GET 请求可以被浏览器或中间缓存保存，所以适合查询这类重复读取。POST 默认不按 GET 的方式缓存，提交表单后刷新页面时，浏览器通常会询问是否重新提交。

需要注意，POST 本身不等于安全。数据放在请求体里只是不直接出现在 URL 中，真正保护传输内容仍然要靠 HTTPS。GET 请求需要对参数进行 URL 编码，也不意味着只能传 ASCII 字符。

所以，查询数据通常用 GET，提交或修改数据通常用 POST。

#### SQL 索引失效该怎么解决？

执行计划选择全表扫描，并不一定说明索引坏了。优化器会比较走索引和全表扫描的成本，有时全表扫描确实更便宜。常见导致索引无法有效使用的情况有：

1. 查询条件不符合联合索引的最左匹配原则。
2. 索引列和参数发生隐式类型转换。
3. 在索引列上使用函数或表达式。
4. 使用前置通配符模糊查询，例如 `LIKE '%关键词'`。

排查时先打开慢查询日志，再用 `EXPLAIN` 查看执行计划。重点看 `type`、`key`、`rows`、`Extra` 等字段，确认有没有命中预期索引、扫描了多少行，以及是否出现文件排序、临时表等高成本操作。

如果返回行数明显过多，要检查过滤条件是否足够精确。子查询也可以结合实际场景改写为 `JOIN`，但是否更快仍要以执行计划为准。

### ConcurrentHashMap 如何保证线程安全？

JDK 7 和 JDK 8 的实现不同。JDK 7 主要使用分段锁：把哈希表拆成多个 Segment，不同线程操作不同段时可以并行，减少锁竞争。

JDK 8 改成了 CAS 加 `synchronized`。插入元素时，如果目标哈希桶为空，就用 CAS 写入；如果桶中已经有节点，就锁住这个桶的头节点，再操作链表或红黑树。锁的范围从整个 Segment 缩小到单个桶，并发度更高。

### MySQL 的隔离级别

MySQL 的四种事务隔离级别是读未提交、读已提交、可重复读和串行化，它们主要处理脏读、不可重复读和幻读。

* 脏读：一个事务读到了另一个事务尚未提交的数据。对方回滚后，读到的内容就是脏数据。
* 不可重复读：同一事务内两次读取同一行，结果不同，因为中间有事务修改并提交了这行数据。
* 幻读：同一事务内两次按相同条件查询，第二次多出了符合条件的新行，因为中间有事务插入并提交了数据。

读未提交允许脏读。读已提交解决了脏读，但仍可能出现不可重复读。可重复读避免了不可重复读，InnoDB 还会结合 MVCC 和间隙锁处理幻读。串行化提供最强的隔离，但并发能力最低。

### 为什么不能先删缓存，再删数据库？

先删缓存、再删数据库，中间存在时间窗口。线程 A 删掉缓存后还没更新数据库，线程 B 读取时发现缓存为空，就可能从数据库读出旧值并写回缓存。等线程 A 完成数据库更新，缓存里留下的仍然是旧数据。

常见做法是先更新数据库，再删除缓存，也就是 Cache Aside。数据库仍是最终的数据源。如果删除缓存失败，可以先重试，再把失败记录交给消息队列异步处理；要求更高的场景可以订阅数据库 binlog 来触发缓存失效。

延迟双删也能降低部分并发窗口，但第二次删除要等多久很难确定，因此不能只靠固定延迟解决所有一致性问题。

### Spring Boot 的自动装配过程

Spring Boot 的自动装配可以理解为：框架提前准备了一批默认配置，再根据项目里实际引入的依赖和用户自定义的 Bean 决定哪些配置应该生效。

大致流程如下：

1. `@SpringBootApplication` 包含 `@EnableAutoConfiguration`，开启自动装配。
2. 自动配置机制读取候选配置类。新版本通常通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 列出自动配置，旧版本使用过 `spring.factories`。
3. 候选配置并不会全部生效。Spring Boot 会根据 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 等条件继续筛选。
4. 符合条件的配置类被导入容器，并注册其中声明的 Bean。比如项目里有数据源依赖，又没有自己定义数据源，Spring Boot 才会补上默认配置。

自动装配解决的是“少写重复配置”，不是完全取代 Spring 的 IoC 容器。

### 微服务的好处

微服务会把订单、用户、首页等功能拆成独立服务。某个服务出故障时，其他服务仍有机会继续运行。

不同服务可以使用适合自身业务的语言和技术栈。例如后端业务使用 Java，推荐算法使用 Python，文件上传服务使用 Go。服务之间通过接口通信，技术选择更灵活。

团队可以按服务划分职责，独立开发、测试和发布。一个服务回滚时，通常不需要一起回滚其他服务。

扩容也更细。高峰期只扩下单服务，不必同时扩容用户、首页等不相关的服务，资源投入更贴近实际负载。

这些好处也伴随分布式事务、网络故障、链路追踪和部署复杂度等成本。拆不拆微服务，要看业务规模和团队能力。

### 如何防止 SQL 注入？

SQL 注入是攻击者把恶意 SQL 片段混进用户输入，再让程序把输入拼进查询语句。

最有效的防线是使用参数化查询或预编译语句，不要把用户输入直接拼进 SQL。输入校验也有必要，例如数字字段只接受数字、日期字段按日期格式校验。

业务账号应遵循最小权限原则，只保留当前业务需要的数据库权限。接口报错时不要返回表名、字段名和完整 SQL，避免给攻击者提供结构信息。

### 缓存穿透、缓存击穿、缓存雪崩怎么分辨？

缓存穿透：请求的数据在缓存和数据库里都不存在，每次都绕过缓存打到数据库。可以缓存空值并设置较短过期时间，也可以配合布隆过滤器提前拦截一定不存在的数据。

缓存击穿：某个热点 Key 过期，大量请求同时访问这个 Key，并一起打到数据库。可以给热点数据设置合理过期策略，也可以用分布式锁让一个请求回源，其他请求等待结果。

缓存雪崩：大量 Key 在同一时间段集中过期，或者缓存服务整体不可用，导致请求一起涌向数据库。常见处理是给过期时间加随机偏移，并做好缓存集群、限流和降级。

### HTTP 和 HTTPS 的区别

HTTP 以明文传输数据。HTTPS 在 HTTP 和传输层之间加入 TLS，通过证书校验身份，并对通信内容加密。

HTTPS 的握手过程更复杂，部署也需要证书，但能降低数据在传输中被窃听和篡改的风险。现在大多数浏览器也会对纯 HTTP 页面给出不安全提示。

### Redis 分布式锁怎么实现？

加锁时要把“设置 Key”和“设置过期时间”放在同一个原子操作里，例如使用 `SET key value NX EX seconds`。如果分开执行，加锁成功后设置过期时间失败，就可能留下永远不释放的锁。

锁的 `value` 应保存当前请求的唯一标识。释放锁前先确认 Key 中的值是不是自己的，再用 Lua 脚本把比较和删除合并成原子操作，避免误删其他线程持有的锁。

如果业务执行时间可能超过锁的过期时间，需要续期机制，例如后台定时检查并延长 TTL。续期任务只能延自己的锁，业务结束后要停止续期并释放锁。
